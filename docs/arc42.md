# Introduction and Goals {#section-introduction-and-goals}

## Requirements Overview {#_requirements_overview}

Soli lets a group of people cover a shared expense by each pledging what they're willing to pay ("pay as you think"), instead of splitting the cost evenly. The full domain vocabulary (Spend, Pledge, Creator, Total, Share Link, Manage Link, and the Open/Unbalanced/Resolved lifecycle) lives in [`CONTEXT.md`](../CONTEXT.md) — this document doesn't repeat it.

## Quality Goals {#_quality_goals}

Derived from decisions made so far, not yet formally ranked:

- **Low friction to participate** — no accounts; a Pledge is just a name and an amount via a link.
- **Trustworthy pledging** — the mechanism (blind bidding while Open, see [ADR-0001](adr/0001-blind-pledging-while-open.md)) matters more than raw performance or scale.
- **Low operational overhead** — single SQLite file, no external services; matches the project's toy-project scope.

# Architecture Constraints {#section-architecture-constraints}

- Written in [Gleam](https://gleam.run), running on the Erlang/OTP BEAM VM (`gleam-version 1.17.0`, `otp-version 29`, pinned in `.github/workflows/test.yml`).
- Runs as a single OTP application: one named `SessionStore` actor owns the one SQLite connection (`soli/session_store.gleam`).
- Storage is SQLite via `sqlight`; schema is managed by [dbmate](https://github.com/amacneil/dbmate) migrations in `db/migrations/`.
- SQL access is generated by `parrot` from hand-written SQL files (`src/sql/*.sql`) rather than an ORM.
- CI enforces `gleam test` and `gleam format --check` on every push/PR to `main`/`master`.

# Context and Scope {#section-context-and-scope}

## Business Context {#_business_context}

Two actors: the **Creator** (creates a Spend, will hold its Manage Link) and **Participants** (open the Share Link, submit or change Pledges). There are no external business systems — settlement is informational only; soli never moves money or integrates a payment provider.

## Technical Context {#_technical_context}

A single HTTP interface, served over `mist` via the `wisp` web framework. Static assets (`pico.pink.css`, `htmx.min.js`) are served from `priv/static`. No outbound external APIs.

# Solution Strategy {#section-solution-strategy}

- **Server-rendered HTML + htmx**, not a client-side SPA: pages are built as Lustre elements and rendered to HTML strings; the `hx` package (htmx bindings) supplies interactivity. Keeps the whole app in Gleam with no separate frontend build.
- **Single actor owns persistence**: all Spend/Pledge state is behind one OTP actor (`SessionStore`) holding the SQLite connection, serializing access instead of a connection pool.
- **Domain rules live at the actor/handler layer.** `CONTEXT.md` is the authoritative vocabulary; [`docs/adr/`](adr/) records decisions like blind pledging that aren't obvious from the code.

## Whitebox Overall System {#_whitebox_overall_system}

Motivation

Contained Building Blocks

:   - **Router** (`soli/router.gleam`) — maps requests to handlers: home (`/`), create a Spend (`/share/new`), view a Spend (`/share/:id`), submit a Pledge (`/share/:id/participate`).
    - **Web/Middleware** (`soli/web.gleam`) — shared request pipeline: static file serving, CSRF protection, crash rescue, request logging.
    - **Pages** (`soli/pages.gleam`) — renders each screen's HTML.
    - **Forms** (`soli/form/*.gleam`) — `formal`-based validation for creating a Spend and submitting a Pledge. `update_soli_session_form.gleam` and `update_participation_form.gleam` exist as empty stubs — editing isn't implemented yet.
    - **SessionStore** (`soli/session_store.gleam`) — the OTP actor owning the SQLite connection; the only component that touches the database. Handles `Get`, `GetSessions`, `New`, `NewParticipation`.
    - **SQL** (`soli/sql.gleam`, `sql/*.sql`) — `parrot`-generated typed query bindings from hand-written SQL.

Important Interfaces

:   - HTTP (`wisp`/`mist`) is the only inbound interface.
    - `SessionStore`'s `Message` type is the only way into persistence — no other module touches `sqlight` directly.

**Naming note:** the code still says "Session" / "Participation" / "share" throughout, while `CONTEXT.md` now defines the canonical terms as **Spend** / **Pledge**. The rename to match the glossary hasn't been applied to the code yet — see Risks and Technical Debts below.

# Runtime View {#section-runtime-view}

## Create a Spend and collect Pledges {#_create_a_spend_and_collect_pledges}

1. Creator submits the "new Spend" form → `router.create_new_share` validates it via `new_soli_session_form`, calls `session_store.new`, which sends `New` to the actor → the actor inserts a row and returns the new Spend's id.
2. A participant opens the Share Link (`/share/:id`) → `get_session_page` fetches the Spend via `Get` and renders it with `pages.soli_session`.
3. A participant submits a Pledge (`/share/:id/participate`) → validated via `new_participation_form`, sent to the actor as `NewParticipation`, inserted via `sql.new_participation`.

Settlement (the Open → Unbalanced/Resolved transition) is not implemented yet — there's no message or handler for it in `SessionStore` today.

# Risks and Technical Debts {#section-technical-risks}

- **Naming mismatch**: code uses "Session" / "Participation" / "share"; the domain glossary now says "Spend" / "Pledge". Needs a rename pass.
- **Settlement is unimplemented**: `SessionStore` has no way to attempt settlement, compute the proportional scale-down, or transition a Spend to `Unbalanced`/`Resolved`.
- **Manage Link doesn't exist yet**: there's currently no separate creator-only URL — anyone holding a Spend's id can do everything a Creator can.
- **`NewParticipation` hardcodes `id: "test"`** (`soli/session_store.gleam:168`) instead of generating a real id — looks like leftover placeholder code.
- Single SQLite connection behind one actor is a throughput ceiling if usage ever grows past toy-project scale.
